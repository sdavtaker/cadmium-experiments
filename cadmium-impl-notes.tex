This section records the formalism choices, simulator capabilities, and
conventions that apply to every experiment in this repository.

% ─────────────────────────────────────────────────────────────────────────────
\subsection*{Foundational References}

The experiments in this repository reproduce models from the literature;
each experiment section cites its source.  Cadmium~\cite{VWRB19} is an
evolution of the sequential PDEVS architecture~\cite{VNWD15}, adding a
compile-time typed port system.  PDEVS is defined in~\cite{ZPK00}.
Stochastic DEVS (STDEVS), which extends PDEVS with probabilistic time
advances and state transitions, is formalised in~\cite{CKW10}.
Quantized State Systems (QSS), which map ODE integration onto DEVS
atomic models, are introduced in~\cite{K04}.

% ─────────────────────────────────────────────────────────────────────────────
\subsection*{Cadmium PDEVS}

Cadmium implements Parallel DEVS (PDEVS)~\cite{ZPK00} following the
sequential call/return architecture of~\cite{VNWD15} with a compile-time
port system introduced in~\cite{VWRB19}.  All simulation steps execute
in a single thread with a call stack linear in the model hierarchy depth.

PDEVS transitions \emph{all} imminent models simultaneously.  At each
time step the set of imminent models $I \subseteq D$ is computed; every
model in $I$ fires its output function $\lambda$ and then its internal
transition $\delta_{\text{int}}$; models not in $I$ that receive routed
output undergo their external transition $\delta_{\text{ext}}$.  When a
model is both imminent and receives external input, the
\textbf{confluence function} $\delta_{\text{con}}$ resolves the two
transitions:
\[
  \delta_{\text{con}}(s, e, x) =
    \delta_{\text{ext}}\!\left(\delta_{\text{int}}(s),\; 0,\; x\right)
  \quad \text{(internal-first, the Cadmium default)}
\]

Multiple simultaneous messages are delivered as a \textbf{message bag}
(\texttt{std::vector<T>} per port), allowing many values per port per step.

% ─────────────────────────────────────────────────────────────────────────────
\subsection*{Cadmium Classic DEVS}

Classic (sequential) DEVS serialises event processing: at each time step
\emph{exactly one} imminent model transitions.  When more than one model
is scheduled at the same time, the \textbf{SELECT} function breaks the
tie:
\[
  \text{SELECT} : 2^D \setminus \{\emptyset\} \to D,\quad
  \text{SELECT}(I) \in I
\]

The chosen model fires its output and internal transition; outputs are
delivered to influenced models as \textbf{message boxes} (at most one
value per port per step); then time advances and the next step begins.
There is no confluence function in Classic DEVS.

% ─────────────────────────────────────────────────────────────────────────────
\subsection*{Cadmium STDEVS}

Stochastic DEVS (STDEVS)~\cite{CKW10} extends PDEVS by allowing the time
advance function $ta(s)$ to return a sample from a probability distribution
rather than a deterministic value, and the transition functions
$\delta_{\text{int}}$, $\delta_{\text{ext}}$, and $\delta_{\text{con}}$ to
depend on random draws as well.  The PDEVS simulation algorithm is
otherwise unchanged: the simulation engine always receives a concrete
(already-sampled) time advance, so it treats the value as deterministic
from that point on.

In Cadmium, STDEVS models are written as ordinary PDEVS atomic models
whose C++ implementations call a random-number generator during
transition or time-advance evaluation.  No special engine mode is
required; the stochastic behaviour lives entirely in the model code.
Ensemble statistics are obtained by running the same coupled model
multiple times and collecting outputs.  The \texttt{TIME} type is
typically \texttt{double} because inter-arrival and service times are
drawn from continuous distributions.

\subsection*{Cadmium QSS1}

Quantized State Systems of order~1 (QSS1)~\cite{K04} integrate systems of
ODEs by representing each state variable $x_i$ as a DEVS atomic model
called a \emph{quantized integrator}.  The integrator maintains a
piecewise-constant approximation $q_i$ of $x_i$, updated in discrete
jumps of size $\Delta q_i$.

\paragraph{Quantized integrator dynamics.}
Given the current derivative $u_i$ (received as an external input) and the
current quantized state $q_i$, the time advance to the next quantization
boundary crossing is:
\[
  \sigma_i = \frac{\Delta q_i}{\lvert u_i \rvert}, \quad
  \sigma_i = \infty \text{ when } u_i = 0.
\]
At $\sigma_i$ the integrator fires, updates $q_i \leftarrow q_i +
\operatorname{sgn}(u_i)\,\Delta q_i$, and emits the new value to all
connected models.  Receiving models recompute their derivatives and, if
they are also integrators, reschedule their own next event.

\paragraph{Step-size control.}
The quantization $\Delta q_i$ is the sole accuracy parameter: smaller
$\Delta q_i$ gives higher accuracy and more events.  A lower bound
$\Delta q_i > \delta_{\min}$ must be chosen large enough to prevent
Zeno behaviour (infinite events in finite time) when the system has a
stable equilibrium at a quantization boundary.

\paragraph{Cadmium implementation.}
QSS1 models in this repository are standard Cadmium PDEVS atomic models
where the time advance evaluates $\Delta q / \lvert u \rvert$.  The
\texttt{TIME} type is \texttt{double}; passive state is encoded as
\texttt{std::numeric\_limits<double>::infinity()}.  Derivative functions
that combine outputs from multiple integrators are implemented as separate
stateless atomic models receiving bags of values from connected ports.

% ─────────────────────────────────────────────────────────────────────────────
\subsection*{Port System}

All four formalisms in Cadmium use a \textbf{strongly typed port system}.
Each port is a distinct C++ type carrying a specific message type;
couplings are expressed as \texttt{(sender-port, receiver-port)} pairs
verified at compile time.  Port types are declared as:

\begin{itemize}
  \item \texttt{cadmium::out\_port<T>} --- output port carrying values of type \texttt{T}
  \item \texttt{cadmium::in\_port<T>}  --- input port carrying values of type \texttt{T}
\end{itemize}

Each model declares its ports via \texttt{using input\_ports} and
\texttt{using output\_ports} type aliases.  The compiler rejects any
coupling where the message types do not match, replacing runtime
encoding conventions with compile-time guarantees.

% ─────────────────────────────────────────────────────────────────────────────
\subsection*{TIME Type}

Cadmium is parameterised over a \texttt{TIME} template argument that
must satisfy \texttt{cadmium::concepts::Time}: totally ordered,
supporting arithmetic operations, and providing
\texttt{std::numeric\_limits<TIME>::infinity()} for passive time advance.

Common choices:

{\small
\begin{center}
\begin{tabular}{@{}llp{5cm}@{}}
  \toprule
  Type & Representation & Risk \\
  \midrule
  \texttt{float}  & IEEE~754 single &
    $1/10$ not exact; errors may break the causality
    chain and are unbounded \\[4pt]
  \texttt{double} & IEEE~754 double &
    same issue, smaller magnitude \\[4pt]
  rational & exact fraction &
    no rounding error; heavier compute \\
  \bottomrule
\end{tabular}
\end{center}}

Each experiment spec states the TIME types it exercises and the expected
impact on simulation correctness.

\subsection*{Log Format}

Cadmium emits structured \textbf{NDJSON} (Newline-Delimited JSON) to
stdout --- one JSON object per line.  Every record carries a wall-clock
timestamp (\texttt{ts}), a severity level (\texttt{level}), a structured
event name (\texttt{event}), and a human-readable message (\texttt{msg}).
Events during the simulation additionally include \texttt{sim\_time},
the logical clock value at that instant.

In these experiments the log will contain:
\begin{itemize}
  \item a \texttt{run\_info} record at simulation start,
  \item \texttt{sim\_state} records per step at \texttt{debug} level
        (state, message routing),
  \item one record per output emitted by the counter model,
  \item a \texttt{run\_info} record at simulation end with wall time.
\end{itemize}

For the complete event schema and log levels, see
\texttt{simulators/cadmium/}\allowbreak\texttt{docs/log-format.md}.
